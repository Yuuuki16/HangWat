# Issue 管理

Issue は作業の背景、範囲、完了条件を明確にするために使います。
実装前に Issue の目的と完了条件を確認し、PR では関連 Issue を必ず参照します。

## Issue の種類

- `feature`: 新機能の追加
- `bug`: 不具合修正
- `refactor`: 振る舞いを変えない内部改善
- `docs`: ドキュメントの追加、修正
- `chore`: 設定、依存関係、開発環境などの雑務
- `design`: 仕様、UI、アーキテクチャの検討

## Issue に書く内容

Issue には次の項目を含めます。

```md
## 背景

なぜこの対応が必要かを書く。

## やること

この Issue で対応する範囲を書く。

## やらないこと

今回扱わない範囲を書く。スコープ肥大化を防ぐために使う。

## 完了条件

レビュー時に完了を判断できる条件を書く。

## 参考

仕様、画面、ログ、関連 PR、外部資料などがあれば貼る。
```

## 運用ルール

- 1 Issue は原則 1 目的にする。
- 大きい Issue は実装前に小さい Issue に分割する。
- 実装 PR は `Closes #123` のように関連 Issue を閉じる。
- 調査だけで終わる Issue は、結論と次のアクションをコメントに残して閉じる。
- 仕様変更が発生した場合は、Issue 本文またはコメントに判断理由を残す。
